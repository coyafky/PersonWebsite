#### 第十一节——商业生图工作流（Production Workflow）

建议我们将前十节的知识真正连接起来，建立一套从需求接收、素材管理、提示词生成、图像制作、批量排版、质量检测到最终交付的完整流程。



## 第十一节：商业生图工作流（Production Workflow）

GPT 生图从 0 到 1 · 第 11 课 · 从需求接收、批量生成到商业交付

前十节，我们学习了 GPT 生图的各项控制能力：

图片比例、构图、风格、镜头、光影、材质、参考图、文字排版和精确约束。

现在，我们要解决一个更实际的问题：

如何将这些分散的生图技巧，整合成一套能够稳定生产 10 张、100 张，甚至 1000 张商业图片的工作系统？

我们继续使用一个真实的业务场景贯穿本节：

> 上司安排制作 100 张新能源汽车电动踏板商品主图。品牌 Logo、排版、背景、摄影风格和卖点文案保持统一；不同图片需要更换车型、车辆参考图和对应的踏板产品。

这一节的学习目标不是再写一段更长的提示词，而是掌握一套可以重复执行、发现错误并持续优化的生产流程。

### 11.1 商业生图的八个生产阶段

END-TO-END IMAGE PRODUCTION PIPELINE

1. 需求接收（Brief）

   确定图片用途、数量、规格、交付标准

2. 素材管理（Assets）

   收集车辆、产品、Logo 与风格参考图

3. 数据与模板（Template）

   拆分常量、变量，建立母版提示词

4. 输入预检查（Preflight）

   核对适配关系、素材完整性与约束冲突

5. 图片生成（Generation）

   组合提示词、引用图片，分批执行

6. 排版合成（Composition）

   叠加准确文字、Logo、卖点与固定版式

7. 质量验收（QA）

   检查产品、车型、结构、文字与视觉一致性

8. 交付与归档（Delivery）

   导出、命名、提交、记录版本与结果

这一流程中，需要把三种能力分开：

| 系统             | 主要职责                                 |
| ---------------- | ---------------------------------------- |
| AI 图像模型      | 生成和修改视觉内容                       |
| 模板与自动化程序 | 读取数据、组合提示词、批量排版、管理文件 |
| 质量控制系统     | 检查结果，决定通过、修复或重试           |

商业生图不是一次模型调用，而是一条有输入、有处理、有验收、有交付的生产流水线。

### 11.2 第一阶段：需求接收（Creative Brief）

上司通常不会一开始就给出完整的图像技术规范。

例如：

> 给我们所有新能源车型做一套电动踏板主图，统一一下风格，越快越好。

这只是业务需求，并不是可直接执行的生产任务。

我们需要把它转换成结构化的 Brief。

#### 需求模板

Image Production Brief

示例

| 项目名称 | 新能源汽车电动踏板商品主图       |
| -------- | -------------------------------- |
| 生产数量 | 100 张                           |
| 发布渠道 | 微信小程序商品列表               |
| 画幅比例 | 1:1                              |
| 统一风格 | 白灰色汽车商业摄影               |
| 动态内容 | 车型、参考图、产品 SKU、车型标题 |
| 固定内容 | 品牌 Logo、排版、统一卖点        |
| 关键要求 | 车型正确、产品适配正确、品牌不变 |
| 交付格式 | PNG / WebP                       |

#### 需求阶段必须识别三个问题

第一，哪些元素必须准确？

例如，车型、产品型号、Logo、价格等。

第二，哪些元素允许 AI 创造？

例如，摄影棚背景、光照氛围、接触阴影等。

第三，哪些元素必须使用原始素材？

例如，需要完全准确的 Logo、二维码，以及不允许改变结构的实物产品。

这三类要求决定后续采用纯生成、局部编辑还是分层合成。

### 11.3 第二阶段：素材管理（Asset Management）

批量生图最大的管理问题之一，是参考素材混乱。

比如制作第 56 张图片时，程序读取错了车辆参考图，或给某个车型匹配了不适用的踏板图片。

因此需要建立可追踪的素材目录。

#### 推荐项目结构

```
image-production/
├── briefs/
│   └── project-brief.md
├── assets/
│   ├── brand/
│   │   └── lanhui-logo.png
│   ├── cars/
│   │   ├── aito-m9.png
│   │   ├── li-l9.png
│   │   └── denza-n9.png
│   ├── products/
│   │   ├── step-a.png
│   │   └── step-b.png
│   └── backgrounds/
├── data/
│   └── products.csv
├── templates/
│   ├── prompt-master.md
│   ├── layout-spec.json
│   └── constraints.md
├── outputs/
│   ├── generated/
│   ├── composed/
│   ├── approved/
│   └── rejected/
├── reports/
│   └── qa-report.csv
└── scripts/
    ├── generate.py
    ├── compose.py
    └── validate.py
```

这套目录结构把素材、数据、模板、生成结果和报告分开。

尤其要注意：原始参考图与最终生成图不能混在一个目录中，否则自动化流程容易引用错误版本。

#### 图片素材也要有元数据

建议记录：

| 字段          | 作用                   |
| ------------- | ---------------------- |
| `asset_id`    | 唯一素材标识           |
| `asset_type`  | 车辆、产品、Logo、背景 |
| `file_path`   | 文件路径               |
| `related_sku` | 关联产品型号           |
| `version`     | 素材版本               |
| `approved`    | 是否已通过审核         |

例如：

`CAR-AITO-M9-001` 可以指向对应的车型参考图，而不是依靠模糊文件名查找。

### 11.4 第三阶段：建立数据驱动的生图系统

我们在第八节已经学习了常量与变量。

这一节需要进一步明确：变量并不只有文字，还包括图片、产品映射与输出配置。

#### 四类输入数据

Global Constants

全局常量

品牌 Logo、画幅、背景、字体、布局

Row Variables

行级变量

车型、车辆图片、产品 SKU、标题

Conditional Variables

条件变量

不同产品对应不同安装角度或卖点

Runtime Settings

运行参数

模型、质量、批次大小、重试策略

#### 数据表结构

| image_id | car_model | car_asset      | product_sku | title   |
| -------- | --------- | -------------- | ----------- | ------- |
| IMG-001  | 问界 M9   | `aito-m9.png`  | STEP-A      | 问界 M9 |
| IMG-002  | 理想 L9   | `li-l9.png`    | STEP-A      | 理想 L9 |
| IMG-003  | 腾势 N9   | `denza-n9.png` | STEP-B      | 腾势 N9 |

`STEP-A` 和 `STEP-B` 仅为演示标识；正式执行时，必须关联已经确认适配的产品资料。

这样每行数据都会形成自己的图像任务，而母版的构图、背景和品牌规范不需要重复填写。

### 11.5 第四阶段：Prompt Assembly（提示词装配）

在真正的生产系统中，建议不要将所有提示词写成一个无法维护的巨大文本文件。

可以拆分为几个独立模块：

Master Prompt

统一视觉、构图、品牌要求

Row Data

车型名称、车辆参考、产品参考

Constraint Pack

P0 / P1 / P2、编辑范围、禁止事项

Output Spec

图片尺寸、格式、留白、安全区域

Final Prompt · 当前任务完整提示词

#### 可直接用于实际工作的母版

## LANHUI · 批量商品主视觉 Prompt V1.0

### 01. 生产目标

为新能源汽车 {{CAR_MODEL}} 制作高质量电动踏板电商商品主视觉。

本次生成的图片后续需要叠加品牌 Logo、车型标题和固定卖点，所以生成阶段不要绘制任何文字。

### 02. 参考图职责

- 图片 A（{{CAR_IMAGE}}）：车辆的外观参考。
- 图片 B（{{PRODUCT_IMAGE}}）：当前 SKU {{PRODUCT_SKU}} 对应的踏板产品参考。
- 图片 C（{{STYLE_IMAGE}}）：统一的摄影风格与光照参考。

车辆外观以图片 A 为准。
踏板产品设计以图片 B 为准。
图片 C 只负责视觉风格，不允许将其中的车型或产品带入最终画面。

### 03. 固定视觉规范

- 比例：1:1。
- 风格：高级汽车商业摄影。
- 背景：白色至浅灰色渐变摄影棚。
- 镜头：三分之四侧前视角。
- 主体：车辆位于画面中央偏下。
- 光线：柔和商业摄影棚光照。
- 阴影：自然、真实的地面接触阴影。
- 构图：预留顶部约 20% 的标题区域。

### 04. 动态主体要求

正确展示 {{CAR_MODEL}} 的车辆造型。

重点表现已经安装的 {{PRODUCT_SKU}} 电动踏板。

踏板与车身安装位置自然，结构应以真实产品图片及经过审核的安装参考资料为准。

### 05. P0 核心约束

- 不改变车辆主要识别特征。
- 不重新设计踏板产品结构。
- 不添加错误的支架或机械结构。
- 不生成其他车型。
- 不在画面上绘制品牌 Logo、中文标题、价格或二维码。

### 06. P1 设计约束

- 背景保持统一。
- 主体占比保持统一。
- 摄影风格和镜头角度尽量统一。
- 车辆主体完整展示。
- 踏板应清楚可见。

### 07. P2 可调整内容

允许根据当前车型结构，调整少量反射、阴影与自然高光。

### 08. 输出与验收

输出符合目标画幅的高质量产品主视觉。

生成后检查车型、产品外观、安装位置、完整性和画面质量。

如果无法可靠保证配件安装结构的真实性，则标记为需要人工复核，不将生成效果图当作真实施工证明。

这里最重要的一点是：生成阶段不需要让 AI 同时绘制 Logo 和中文标题。 把它们留给后续的排版系统，能够显著减少重复修改成本。

### 11.6 第五阶段：输入预检查（Preflight）

这一环节很容易被忽略，但对 100 张图片的批量生产特别重要。

正式调用图像模型之前，先检查数据是否能够支持生成。

输入预检查清单

1. 车辆参考图片存在，能够正常读取。
2. 车型名称与图片内容匹配。
3. 产品 SKU 存在，已确认适用于目标车型。
4. 有足够的产品与安装参考资料。
5. 母版提示词中的变量均有对应数据。
6. 没有互相冲突的 P0 约束。
7. 输出尺寸符合所选生成接口的要求。

例如，一条数据引用了 `STEP-C`，但是素材目录中没有对应的踏板图片，这一条任务就应直接进入 `BLOCKED` 状态。

不要为了凑满 100 张，让 AI 自行设计缺失的实际产品。

### 11.7 第六阶段：批量生成（Batch Generation）

执行时建议采用小批量逐步验证的方式，而不是第一次就连续生成全部图片。

建议的生产顺序

Stage 1

3 张试产

不同车型 / 产品 SKU

Stage 2

10 张小批量

验证一致性

Stage 3

剩余 87 张

正式批量生产

这些数量是教学用的示例，可以根据预算、接口限制和任务风险调整。关键是先验证，再扩大规模。

#### 为什么要先试产？

因为一旦母版提示词存在系统性问题，批量运行就会把错误复制到所有图片中。

例如：100 张图片都把车辆放得太大，导致顶部文字排版区域不足。

如果试产时发现这个问题，只需要修改一次母版。

如果全部生成完才发现，就可能需要大规模返工。

#### 任务状态管理

| 状态         | 含义                       |
| ------------ | -------------------------- |
| `PENDING`    | 等待处理                   |
| `BLOCKED`    | 输入数据不完整或适配未确认 |
| `GENERATING` | 正在调用模型               |
| `GENERATED`  | 主视觉已生成               |
| `COMPOSED`   | 文字与 Logo 已合成         |
| `REVIEW`     | 等待质量审核               |
| `APPROVED`   | 已通过验收                 |
| `FAILED`     | 不合格，需要处理           |

每条任务还应记录生成次数、错误类型、所用模板版本和最终文件路径。

### 11.8 第七阶段：排版合成（Composition）

当 AI 完成车辆主视觉后，进入第二条生产线：确定性图文排版。

统一商品图片母版

LANHUI 蓝辉轻改

专车专用电动踏板

智能伸缩｜安全防夹

动态车辆主视觉

铝合金面板 · 专车适配 · 到店施工

母版排版示意，顶部图标为占位符，实际交付必须使用蓝辉轻改官方 Logo。

在这一环节，推荐使用 HTML/CSS、SVG 或图像合成程序实现排版。

原因是它们可以精确控制：

- 字体和字号。
- 文字位置与对齐。
- 品牌 Logo 的原始图形。
- 安全边距。
- 商品标题及动态数据。
- 最终输出尺寸。

如果后续要修改固定副标题，只需要更新排版母版，不必重新生成所有车辆素材。

### 11.9 第八阶段：质量检测（Quality Assurance）

商业图片的验收不能只评价“好不好看”。

我们需要把质量检测拆成三个层次。

#### L1 · 自动化基础检测

适合通过程序自动完成：

- 文件是否存在。
- 图片是否能够正常打开。
- 宽高比例、像素尺寸是否正确。
- 文件大小是否合理。
- 输出文件名是否符合规则。
- 参考图及 SKU 映射是否完整。
- 已排版的文本数据是否与业务数据一致。

#### L2 · 视觉辅助检测

可以使用视觉模型辅助判断：

- 车辆是否与目标车型大致匹配。
- 主体是否被裁切。
- 背景是否存在明显异常。
- 图片是否出现额外人物、物体。
- 是否符合统一风格。

但这些判断并不总是准确，尤其不应让视觉模型单独确认真实产品适配关系。

#### L3 · 人工业务审核

需要专业人员核对：

- 车型识别细节。
- 踏板是否真实适配。
- 安装效果是否具有误导性。
- 产品规格和卖点是否有依据。
- 需要作为真实施工记录的图片是否确实来自实际施工。

质量检测分流

生成图片 + 对应业务数据

自动检查 · 文件 / 比例 / 数据 / 模板

视觉辅助检查 · 外观 / 结构 / 布局

人工业务复核 · 产品真实性

APPROVED

进入正式交付

FAILED / REVIEW

修复或重试

#### 失败后怎么处理？

建议按照问题类型选择修复方式。

| 错误类型           | 处理方式                     |
| ------------------ | ---------------------------- |
| 背景不理想         | 局部编辑背景或重新生成       |
| 画幅错误           | 检查输出配置及裁切规则       |
| 中文错别字         | 修改排版层，重新导出         |
| Logo 错误          | 使用原始品牌素材替换         |
| 车型结构错误       | 回到正确车型参考图重新生成   |
| 踏板结构或适配错误 | 暂停任务，核对真实产品资料   |
| 车辆主体位置不统一 | 调整母版 Prompt 或标准化合成 |
| 多轮编辑导致漂移   | 回退到最近的合格版本         |

尤其要注意：如果错误来自母版，不应该只修复当前图片，而应该先修改母版，再检查所有使用该版本生成的图片。

### 11.10 第九阶段：交付与归档（Delivery & Archiving）

虽然实际主流程可归纳为八个阶段，但在正式项目中，值得将交付单独作为管理环节。

一个可交付的图片批次，除了最终图片，还应保留生产记录。

推荐输出目录：

```
delivery/
├── approved-images/
│   ├── IMG-001-aito-m9.png
│   ├── IMG-002-li-l9.png
│   └── IMG-003-denza-n9.png
├── thumbnails/
├── manifest.csv
├── qa-report.csv
├── template-version.txt
└── delivery-notes.md
```

其中：

`manifest.csv` 用于记录图片与车型、SKU 的对应关系。

`qa-report.csv` 用于记录通过与失败的检查项。

`template-version.txt` 用于标识当前使用的母版版本。

这些文件能够帮助后续人员找到图片来源，以及在发生产品或文案更新时快速重新生产。

### 11.12 完整的商业生图任务规范

这是我建议你后续交给 Hermes Agent、Python 脚本或其他自动化系统使用的任务说明。

## AI Commercial Image Production · Workflow Spec V1.0

### 一、项目目标

为指定商品数据批量生成符合品牌规范的商业视觉图片。

### 二、输入

- 业务需求 Brief
- 商品与车型数据表
- 车辆参考图片
- 产品真实参考图片
- 原始品牌 Logo
- 视觉风格参考
- 排版母版
- 质量验收规则

### 三、生产流程

#### Step 1 · 读取任务

获取所有商品记录。

检查商品名称、车型、SKU、参考图片和输出要求。

#### Step 2 · 素材预检查

确认所有必要文件存在。

确认车型与产品适配关系已经经过业务验证。

缺少关键资料的任务标记为 BLOCKED，不允许自行编造。

#### Step 3 · 装配提示词

加载 Master Prompt。

注入当前行的变量。

加载对应的车辆与产品参考图。

加载 P0/P1/P2 约束。

生成本次任务的最终 Prompt。

#### Step 4 · 生成主视觉

调用可用的图像生成接口。

生成不含品牌文字、Logo、二维码的产品主视觉。

保存输出、任务 ID、模型信息、模板版本与生成记录。

#### Step 5 · 图文合成

使用固定排版模板。

叠加原始品牌 Logo。

通过真实字体渲染商品名称、卖点和其他信息。

严格遵守画幅与安全区域要求。

#### Step 6 · 质量检测

执行自动文件检查。

执行视觉辅助检查。

对产品适配、结构与宣传真实性进行人工复核。

出现 P0 错误时不得通过验收。

#### Step 7 · 失败处理

区分数据、生成、排版和业务错误。

可自动修复的问题执行有限次数重试。

无法确认的产品问题交由人工处理。

禁止无限重试。

#### Step 8 · 输出交付

导出合格图片。

统一文件命名。

生成任务清单、质量报告与交付说明。

#### Step 9 · 版本归档

保存母版版本。

保存原始素材与输入数据映射。

保留通过验收的主视觉与最终成品。

支持后续产品更新与重新生成。

### 四、系统约束

- 不得伪造产品参数、安装效果和适配信息。
- 不得重新绘制要求完全一致的 Logo 或二维码。
- 不得把 AI 效果图标记成真实施工照片。
- 生成失败必须记录原因。
- 所有最终交付素材必须可追溯。
- 母版更新必须具有版本记录。

### 五、完成标准

只有满足以下条件的图片才进入正式交付：

1. 图片文件有效。
2. 主体与数据匹配。
3. 产品结构和适配经过确认。
4. 品牌及文字准确。
5. 构图与视觉风格符合母版要求。
6. 通过最终审核。

### 11.14 本节总结：从 Prompt Engineering 到 Image Production Engineering

通过前十节，我们主要掌握的是控制单张图片的能力。

第十一节开始，我们建立的是组织一批图片生产任务的能力。

可以用下面的公式总结：

商业生图系统 = 标准化需求 + 素材管理 + 结构化数据 + Prompt 母版 + 自动化生成 + 确定性排版 + 质量验收 + 版本归档。

我们最终追求的不是“100 张图片能不能生成出来”，而是：

能否把 100 张图片生产成一批风格统一、内容准确、修改成本可控、能够正式交付的商业素材。
