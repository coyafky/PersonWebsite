# 知识库 v2.0：把「不同主体的事实不能混」写成铁律

> 📌 本篇由当日记忆笔记重建。

## 🤖 全量改造

按一份企业知识库规范，把自建知识库从 1.x 改到 **2.0**。核心是**增量注册，不动知识库的物理结构** —— 避免为了架构整洁而冒着丢内容的风险。

改造内容：

| 层 | 内容 |
|---|---|
| 配置层 | 知识域 / 来源优先级 / 关系类型 / 权限 / 生命周期 / 检索 / 评测 + 字段规范 |
| **Schema 层** | 实体 / 来源 / 关系 / 上下文包 / 评测项，**五份 JSON Schema** |
| 提示词层 | 编译 / 解析 / 审计 / 上下文编译 / 修复，**五件套** |
| 工作区 | 原始（**不可变**）+ 规范化 / 注册表库 / 暂存 / 运行记录 / 评测骨架 |
| 工具 | 新增建注册表 / 检查 / 陈旧检测 / 信任度 / 来源 / 索引信息等子命令，**27 个测试全绿** |

顺带修了一个时区 bug。

## ⚠️ 一条最重要的铁律：主体边界

真实做了一次导入演练：把一份外部服务手册（1225 行）导进来 → 登记来源 + 规范化出 8 条规格候选 → 全库注册表变成 **180 个实体 / 61 个别名 / 46 条关系**。

**但过程中确认了一件关键的事：**

> **那份外部手册与自家业务属于不同主体，事实绝不混同。**

这条被写进了十五铁律。理由很实在：**两个主体的信息一旦混进同一张表，之后所有"这个数字是谁的"都无法回答。** 混一次容易，拆干净很难。

## 关键决策

| 决策 | 理由 |
|---|---|
| **增量注册，不动物理结构** | 不做大搬迁，避免丢内容 |
| **主体边界写进铁律** | 不同主体的事实混同后无法追溯归属 |
| 原始来源目录设为不可变 | 规范化产物可重建，原始素材不能丢 |
| 新增导入技能固化流程 | 主体边界 / 只追加 / 规范化 / 冲突识别 / 注册表重建 |
